## Сравнение и границы

A (mode 0) уже содержит исправление распределения ресурсного кэша и подготовку
моделей/анимаций. B (mode 1) добавляет к нему все три остальных кандидата:
80% штатного кэш-параметра, веса NiSeq RAM/VRAM 100/100; буферное переиспользование
r6; Find per-call cache build-r3. Таким образом, сравниваются базовый ресурсный
фикс и полный набор четырёх. Это не all-four OFF/ON и не замер добавочного
выигрыша относительно одного Find cache; проценты прошлых опытов не складывать.

Порядок A/B/B/A, четыре свежих двухпользовательских матча с одним frozen
setup-r3. SHA всех driver inputs, observer, helper EXE, d3d9.dll, GPU bridge
и Find DLL одинаковые в когорте; меняются только три режима и настройка кэша.
Исправленный ресурсный код общий. Полный набор подтверждён живыми квотами,
весами/потреблением NiSeq, штатными счётчиками подготовки, реальными попаданиями
буферов и миллионами пропусков Find. Ноль событий давления памяти.

Одна копия Случайно2 (карта 1280, 20 своих рот), одинаковые три центра/ID камеры,
масштаб 2,0, настоящие окна 2560×1440, лимит 30 fps. Три обхода по 15 секунд на
общей паузе, затем >60 секунд работающей симуляции у каждого участника. Перед
паузой остаются небольшие различия времени/анимации/положения войск. GPU prewarm,
prepared-view cache, scene slots, D3D state cache, старый index/reject и nested
scope hooks выключены. ОС/драйверные кэши не очищались.

Это сокращение амплитуды пиков в данной серии, а не гарантированное улучшение

эффекта. Большие рывки остаются, постоянный uncapped FPS не измерялся.

NiSeq считает KF по искусственной оценке file-size ×60. Последняя строка не
является реальным расходом RAM или VRAM. Счётчик игры также не равен полному
расходу памяти драйвера. Свободное адресное пространство снято из самого
32-битного процесса; общий CPU/RAM — раз в секунду, GPU memory — после камеры.
80/100/100 здесь диагностическая настройка, не новое значение по умолчанию.
Обычное вытеснение остаётся штатным. Порог остановки QA: 512 МиБ свободного VA,
384 МиБ доступной физической RAM или global memory load от 90%.

## Безопасность стенда и ранние ошибки

Статистика кэшей копируется под родной metadata lock только после завершения
всей цепочки кадра. Запись файлов выполняется после освобождения lock.
Запросов/ожиданий загрузки под этой блокировкой нет, указатели на модели не
сохраняются. Не ставятся дополнительные входные перехваты NIF/KF Load: число
загрузок отдельно в этой серии не измерялось. Подготовка проверяется штатными
счётчиками helper, а удержание анимаций — живыми квотами/использованием кэша.

Ранний setup (R1) завис на старте: metadata sampling находился в произвольном
QPC callback, который мог уже держать блокировку. setup-r2 перенёс его на конец
кадра. Его A-контроль прошёл, но B получил Access Violation при вызове
ReweightCachesFromUVars: anonymous pointer cast потерял fastcall в TinyCC,
ECX был 0, ошибка чтения адреса 4 в RVA 1B54DA. Применён именованный fastcall
typedef. Шесть проверок actual compiled caller при трёх базах воспроизводят
старую ошибку и подтверждают правильные ECX/EDX/ESP для r3. Это фрагмент вызова
с моделью memory-getter leaf, не эмуляция всей игры. Файлы ошибок/дамп сохранены.
R1/R2 и удачный старый R2 контроль не входят в сравнение производительности.
Ни одна из этих попыток не затронула установленную игру.
