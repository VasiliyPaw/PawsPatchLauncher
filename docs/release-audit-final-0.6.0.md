## Итог

Кандидат проходит перечисленные ниже автоматические проверки. Свежая сборка побайтно совпадает с ранее переданной пользователю и VM сборкой `resources-polish`; новых изменений поведения клиента в этом аудите нет. Подготовлен локальный архив, **релиз, тег, подписанные feed и сервер не менялись**.

Безоговорочную отметку «всё проверено, можно публиковать» не ставим. Перед выпуском остаются:

1. **Установить причину четырёх серверных ответов 5xx за последние 24 часа.** Во время аудита счётчик не вырос, текущие проверки сервисов успешны. Это не доказывает, что причина устранена. Подробные журналы через текущее подключение недоступны: ранее получен `Insufficient scope`; обход ограничений и использование других секретов не выполнялись.
2. **Указать ручной способ перехода для старого обновлятора на длинных путях.** Публичная 0.5.8 успешно обновляется своим механизмом на обычном пути. При длине пути файла подтверждения 273 символа она откатывает успешно запущенный кандидат. В 0.6.0 механизм исправлен, но исправление не может изменить код уже установленной 0.5.8. Для затронутого пользователя: закрыть лаунчер и однократно заменить EXE на файл из проверенного официального выпуска, сохранив остальные файлы. Подписи/хеши будущего публичного файла нужно проверить после публикации.
3. **Подготовить точный состав релизного коммита и окончательный текст выпуска.** Рабочее дерево содержит много незакоммиченных и новых исходников, тестов, миграций. Есть временный WPF-проект и `tools/__pycache__`; их не следует включать в релизный коммит. Ничего автоматически не удалялось и не добавлялось в индекс. `docs/release-0.6.0.md` пока начинается служебной пометкой о черновике; workflow публикует этот файл целиком, поэтому при утверждении выпуска пометку нужно убрать.

Это не новая регрессия интерфейса. Разработка дополнительных функций перед 0.6.0 сейчас не требуется.

### Достоверность проверки старого обновлятора

`tools/AuditPublicRelease.ps1` скачал публичный EXE, проверив его по подписанному Stable feed. SHA-256 публичной 0.5.8:

`19ACD915FFFFF83DF24F2BC31DF0DF6A7BA8106986B265EA6C3D0EFBA27BCED9`

Использованы штатная SDK-библиотека HostModel и [описание структуры bundle в исходниках .NET](https://github.com/dotnet/runtime/blob/v8.0.0/src/installer/managed/Microsoft.NET.HostModel/Bundle/Manifest.cs).

Изменения сгенерированного старого скрипта в тесте ограничены добавлением `--smoke-test` каждому дочернему лаунчеру и тайм-аутом 15 секунд. Подписи/серверы/конфигурация пользователя не подменялись; проверка скачивания кандидата старым UI здесь не выполнялась.

- Обычный Unicode-путь: длина пути ACK **131**, замена на 0.6.0 подтверждена; результат имеет хеш кандидата.
- Длинный Unicode-путь: длина ACK **273**, готовая 0.6.0 создала правильный токен, однако старый скрипт его не увидел и восстановил 0.5.8. Хеш восстановленного EXE совпал с публичным оригиналом.
- Дополнительный read-only замер Windows PowerShell: `File.Exists` для этого ACK — `false`; для того же файла с расширенным префиксом — `true`. Следовательно, это ограничение файловых API старого помощника, а не отсутствие запуска нового окна.
- Новая реализация использует расширенные пути для файловых операций и прошла реальную замену в глубоком каталоге.

Фикстуры старого обновлятора сохранены в `C:/Users/Paw/Documents/Codex/paw-legacy-audit-060-3`. Предыдущие две попытки диагностического инструмента остановились до запуска помощника из-за обработки квадратных скобок PowerShell и типов аргументов отражения; диагностический инструмент исправлен, продукт не менялся. Все запущенные этим инструментом копии закрыты; пользовательский лаунчер не закрывался.

Первый запуск отдельного старого .NET Framework процесса-фикстуры в глубоком каталоге не создал длинный ACK, из-за чего сценарий `healthy` правильно откатился. Повтор на пути без этого ограничения прошёл для healthy/crash/timeout. Этот инфраструктурный сбой не скрыт и не считается поломкой реального EXE: реальная 0.6.0 на длинном пути ACK создаёт.

### Замечания безопасности и роста

- В Auth отключена проверка скомпрометированных паролей. Это отдельное усиление защиты, не доказанный сбой текущей регистрации. См. [официальное описание проверки паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
- Советник перечисляет SECURITY DEFINER-функции, доступные anon/authenticated. Многие являются намеренными RPC с внутренней проверкой прав; это не основание массово отбирать доступ. Изолированные тесты прав проходят, но абсолютная безопасность всех путей этим не доказана.
- Информационные замечания об отсутствующих индексах: `archived_chats(peer_id)`, `hidden_chats(peer_id)`, `official_chats(high_id)`, `social_offers(sender_id)`, `paw_friendships(requester)`. Перед заметным ростом пользователей стоит проверить планы запросов/удалений и добавить нужные индексы. См. [советник внешних ключей](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys). Это не текущая ошибка при данном объёме данных.
- EXE **не имеет Authenticode-подписи издателя**. Подписи feed защищают загрузку обновления, но не заменяют подпись EXE. Решение о сертификате и репутации распространения — отдельно.
- GitHub CI пока запускает основной клиентский набор, а не SQL/Edge/WPF-набор этого аудита. Перед последующими выпусками полезно закрепить эти проверки в автоматическом процессе.
